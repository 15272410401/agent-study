# Agent 认知

### 模式对比

| 场景      | ChatGPT 模式         | Agent 模式                                   |
| --------- | -------------------- | -------------------------------------------- |
| 你的输入  | "帮我写一个排序函数" | "帮我把这个 Bug 修了"                        |
| AI 做什么 | 输出一段代码         | 读文件 → 定位 Bug → 分析原因 → 写修复 → 验证 |
| 你做什么  | 复制粘贴、人肉跑程序 | **看它做**                                   |
| 交互次数  | 1 次                 | 5+ 次自动循环                                |

Agent 的理念不是重回命令行，而是为场景定制更自动化、更好用的工具。

### 核心概念

Agent 的核心是一个 **大语言模型（LLM）**=> GPT、DeepSeek、豆包。它负责：

- 理解你的意图
- 推理问题的解决方案
- 生成回复文本

但 **LLM 只能输出文本**。它不能读文件、不能调 API、不能执行代码。

因此 **Agent Loop（智能体循环）**机制使 agent 变得更 **自主、灵活、可纠错、能持续完成任务，从而从一次性回答者变成可持续执行复杂任务的自主智能体。**

=> 它的动作模式是：**感知·思考·行动·反馈**。

及 **LLM 是大脑，Agent Loop 是神经系统和四肢。大脑负责产生信号，循环负责驱动行动**。

#### 循环图

```Plain
感知 → 思考 → 行动 → 观察/反馈 → 感知 → 思考 → 行动 → …（直到任务完成）
```

#### LLM vs Agent

|          | LLM 问答          | Agent                             |
| -------- | ----------------- | --------------------------------- |
| 步骤数   | 1 步（输入→输出） | N 步（循环直到完成）              |
| 能力边界 | 只能输出文本      | 能调工具、能执行、能验证          |
| 你会看到 | 一段回答          | 一个过程——读文件→分析→写代码→测试 |

### Agent执行拆解及深度认识

#### 1 — Agent 会反问

你想想你平时用 ChatGPT——你问什么它答什么，从来不会反问你。但 Agent 会问：

- "你确认是这个意思吗？"
- "这个模块在三个地方被引用了，你希望我全部改还是只改 A？"
- "有两个方案可以达到你的目标，方案 X 更快但改动大，方案 Y 更安全——你选哪个？"

| 维度       | 内容                                                         |
| ---------- | ------------------------------------------------------------ |
| ReAct 阶段 | **感知（Perception）**                                       |
| 打破认知   | AI 可以是主动的 —— 它在确认自己有没有理解对                  |
| 类比       | 好同事 vs 差同事 —— 好同事先问清楚再动手，差同事闷头改完你发现全改错了 |

> Agent 的第一步不是「回答」，是感知。它在确认自己有没有理解对。
>
> 这就像你让一个新同事帮忙改代码 —— 好的同事会先问清楚再动手，差的同事闷头改完你发现全改错了。
>
> Agent 的第一步永远是感知 —— 先搞清楚状况。

#### 2 — Agent 会跨文件检索

你说「把 `getUser` 函数改成异步的」——Agent 不只改 `user.ts`，它会全局搜索 `getUser` 的调用点、检查类型定义、看测试用例是否需要更新。

| 维度       | 内容                                        |
| ---------- | ------------------------------------------- |
| ReAct 阶段 | **感知（Perception）** — 建立全局上下文     |
| 打破认知   | 改 A 可能影响 B —— Agent 比你更谨慎         |
| 使用的工具 | `search_content`、`read_file`、`list_files` |

> 换我们人做这件事，你是不是要全局搜索一下？看看这个函数在哪些地方被调用了。Agent 做了同样的事——但比你快 100 倍。
>
> 这就是感知的第二步：建立全局上下文。Agent 不是瞎子，它有工具——这些工具就是它的眼睛。

#### 3 — Agent 会规划

你给它一个需求：「把项目的 API 从 REST 改成 GraphQL」—— 它不会说「好的」然后开始瞎改。它会：

1. 先分析哪些模块受影响
2. schema 怎么定义
3. resolver 怎么写
4. 测试怎么改
5. 然后按依赖关系排序 —— 先改 schema，再改 resolver，最后改测试
6. 甚至会启动 subagent 并行执行独立任务

| 维度       | 内容                                            |
| ---------- | ----------------------------------------------- |
| ReAct 阶段 | **思考（Reasoning）** — 规划与分解              |
| 打破认知   | AI 能规划——这不是简单的「下一步」，这是依赖分析 |
| 关键技术   | Subagent 调度、任务依赖分析                     |

> 规划过程也是 **思考（Reasoning）**的过程。LLM 可以推理，但只有 Agent 能在推理的基础上做规划。
>
> LLM：你问什么它想什么。
>
> Agent：你给一个目标，它自己想出拆解路径、执行顺序、异常处理（因为 Agent 与物理世界是打通的）
>
> 这就是为什么 Agent 不是「高级 ChatGPT」。

#### 4 — Agent 会行动并自检

它不是输出一段代码让你复制粘贴。它真的在调文件系统、在写文件、在跑命令、在执行测试。你看着终端一行行输出，文件一个个被修改——你变成了指挥者而不是执行者。

> 更令人惊讶的是——改完之后它会自己检查。

- 读回修改的文件
- 运行测试
- 检查 lint
- 如果发现问题 → 自己修正 → 重新进入感知 → 思考 → 行动 → 观察/反馈的新一轮循环

| 维度       | 内容                                                      |
| ---------- | --------------------------------------------------------- |
| ReAct 阶段 | **行动（Acting）→ 观察/反馈（Feedback）**                 |
| 打破认知   | 不是输出代码让你复制粘贴 —— 它真的在写；写完了还自己检查  |
| 你会看到的 | 终端一行行输出，文件一个个被修改——然后自动跑测试、看 lint |
| 关键价值   | 行动之后必须观察 —— 没有观察，Agent 就不知道自己做没做对  |

> 注意：它不是输出一段代码让你复制粘贴。它是真的在调文件系统、在写文件、在跑命令、在执行测试。
>
> 更关键的是——它做完了不会说「应该可以了」。它会自己检查。检查到的结果会成为下一轮感知的输入——这就是循环闭合。
>
> 你想想 —— 人写代码写完也会跑测试对吧？Agent 做了一样的事。但区别是，如果测试失败了，它不需要等你告诉它——它自己就去改了。

#### 5 — 总结

行动和观察/反馈是连在一起的。这就是‘闭环控制’。没有观察/反馈的 Agent 只是在发指令，有了反馈并能自我修正的 Loop 才是‘数字员工’。

\> **感知（看）→ 思考（想）→ 行动（做）→ 观察/反馈（验）→ 感知 → ……**

> 这就是 ReAct 循环。现在它成了几乎所有 Agent 的底层架构。

### 原理抽象 — 从现象到 ReAct 循环

**ReAct => 思考 Reasoning + 行动 Acting**

> 学术锚点：Yao et al., "ReAct: Synergizing Reasoning and Acting in Language Models", ICLR 2023
>
> 论文地址：https://react-lm.github.io/
>
> 开源实现（姚顺雨，腾讯首席 AI 科学家）：https://github.com/ysymyth/ReAct

#### 核心思想

将推理（Thought）与行动（Action）交错执行 —— 每一步行动后观察/反馈结果（Feedback），再进入下一轮思考。

- 纯推理（Chain-of-Thought）：能想但不能做
- 纯行动（只调工具）：能做但不会想
- ReAct（想+做交错）：**控制流与推理的共生。利用循环将 LLM 的“瞬时推理”转化为“长期任务执行力”，并在每一次迭代中动态管理上下文窗口。**

#### 架构概览

```Plain
用户任务
  ↓
System Prompt（人格定义）
  ↓
┌──→ LLM 推理（Thought + Action）
│      ↓
│<-—— 有 tool_call？─── 是 ──→ 执行工具（Action）
│      │                         ↓
│      │                    得到结果（Feedback）
│      │                         ↓
│      │                    注入对话历史
│      └─────── 循环 ←─────────┘
│
否 ──→ 输出最终答案（Final Answer）
```

#### 核心代码解读

① System Prompt — Agent 的人格

```TypeScript
const messages = [
  {
    role: "system",
    content:
      "你是一个 ReAct Agent。使用 Thought → Action → Feedback 循环完成任务。" +
      "每一步只调用一个工具。当任务完成时，直接回复最终答案，不要再调用工具。",
  },
  { role: "user", content: task },
];
```

> 注意：System Prompt 就是 Agent 的「人格宪法」—— 它定义了 Agent 的行为边界和工作方式。

② 循环体 — 感知→思考→行动→观察/反馈

```TypeScript
//MAX_ITERATIONS,防止逻辑死锁（Logic Deadlock）的硬护栏，避免无限消耗 Token。
for (let i = 1; i <= MAX_ITERATIONS; i++) {
  // Step 1: 调用 LLM — Thought + Action
  const response = await client.chat.completions.create({
    model: MODEL,
    messages,     // ← 每轮把完整对话历史传给 LLM
    tools: TOOLS, // ← 告诉 LLM 有哪些工具可用
    tool_choice: "auto",
    temperature: 0,
  });

  const msg = response.choices[0].message;

  // Step 2-a: LLM 要求执行工具 → Action
  if (msg.tool_calls && msg.tool_calls.length > 0) {
    const fnName = toolCall.function.name;
    const fnArgs = toolCall.function.arguments;

    // 执行工具
    const Feedback = await executeTool(fnName, fnArgs);

    // 将结果注入对话历史
    messages.push(msg);           // LLM 的 tool_call 请求
    messages.push({               // 工具执行结果 = Feedback
      role: "tool",
      tool_call_id: toolCall.id,
      content: Feedback,
    });
  }
  // Step 2-b: LLM 直接回复 → Final Answer
  else {
    return msg.content;  // 任务完成
  }
}
```

#### 关键设计点

| 设计点                | 说明                       | 为什么重要                       |
| --------------------- | -------------------------- | -------------------------------- |
| `MAX_ITERATIONS`      | 最多循环次数（默认 10）    | 防止 Agent 无限循环              |
| `messages` 追加       | 每轮把工具结果重新注入对话 | 这就是 Agent 的「短期记忆」      |
| `tool_choice: "auto"` | LLM 自行决定是否调工具     | 不需要人判断「现在该不该调工具」 |
| `temperature: 0`      | 确定性输出                 | 保证课堂演示结果可复现           |

#### 总结 Agent 的本质

| 你的认知     | 在 lesson1-reAct 里对应什么 | 本质                           |
| ------------ | --------------------------- | ------------------------------ |
| Agent 有记忆 | `messages` 数组             | 完整对话历史，每轮重新发送     |
| Agent 会思考 | LLM 推理 `tool_choice`      | LLM 判断「现在需不需要调工具」 |
| Agent 会行动 | `executeTool()`             | 客户端真正执行函数             |
| Agent 会观察 | `messages.push(Feedback)`   | 工具结果重新注入               |

### Agent 能力全景图 — 驾驭工程框架图（Harness Engineering Map）

#### Harness Engineering Map（Harness工程 <==> 驾驭工程）

\- 上下文域 = Agent 的**眼睛和记忆**（输入）

\- 工具域 = Agent 的**手**（执行）

\- 协议域 = Agent 的 **嘴**（交互标准）


#### 上下文域

\> 上下文域的核心逻辑是 —— **你给 LLM 看什么，它就基于什么做决策。**不是 Agent 聪明，是把聪明的东西放进了它眼前。

**① System Prompt — Agent 的「人格宪法」**

```Plain
你是资深 TypeScript 工程师。分析代码结构后再回答。
遇到不确定的事，反问确认后再行动。
```

每一轮对话的最前面塞进这段 System Prompt——它定义了 Agent 的行为边界和工作方式。

> 「和 User Prompt 有什么区别？」→ System Prompt 持久约束行为（通用于所有对话），User Prompt 是单轮指令（只对这一次对话有效）

**② Rules 文件 — 项目级持久化规则**

- `Claude.md`（Claude Code 专用）
- `.cursorrules`（Cursor 专用）
- `.github/copilot-instructions.md`（Copilot 专用）

这些纯文本文件在每轮对话中被注入上下文，形成 Agent 的「项目工作习惯」。

> 「和 System Prompt 有什么不同？」→ Rules 是文件级持久化（团队共享），System Prompt 是会话级指令（工具/平台定义）

**③ RAG（检索增强生成）**

Agent 从外部知识库（公司文档、API 文档）检索相关内容，拼入 Prompt 再推理。

> 「和 Web Search 有什么区别？」→ RAG 搜私有库，Web Search 搜公网。

**④ Memory（短期/长期）**

- 短期：当前对话历史。每轮把完整历史重新发送给 LLM
- 长期：跨会话持久化记忆。需要显式实现（向量数据库 + 摘要）

> 「多轮对话怎么记住的？」→ 每轮把完整历史再发一遍。「关了再开会忘记吗？」→ 会，因此需要显式持久化

**⑤ Context Window — 物理天花板**

如 GPT-4o 128K tokens ≈ 一本中篇小说。超了就裁剪——这是 Agent 的硬限制。

> 「为什么聊久了会忘记前面？」→ 超出 Context Window 的内容被裁剪了。

Agent 的行为约束，就是由这样的纯文本定义的。

#### 工具域

\> LLM 是大脑，Tools 是手 —— Function Calling 就是大脑告诉手「去拿那个杯子」的方式。

| 工具                   | 说明                             | 典型场景                  |
| ---------------------- | -------------------------------- | ------------------------- |
| **Function Calling**   | 模型输出 JSON 描述调哪个函数     | 所有 AI 工具的底层机制    |
| **Custom Tools**       | 开发者定义的任意工具             | 查数据库、发邮件、建 Jira |
| **Computer Use**       | 模拟人类操作 GUI（图形用户界面） | 填表单、点按钮            |
| **Code Interpreter**   | 沙箱执行代码                     | 数据分析、图表生成        |
| **File System**        | 读写本地文件                     | 读源码、写代码            |
| **Browser Automation** | 控制浏览器                       | 抓取网页、自动填表        |

**Function Calling 的本质**

```JSON
// LLM 的输出不是自然语言，而是这个结构化的 JSON:
{
  "name": "read_file",
  "arguments": {
    "path": "/src/services/user.ts"
  }
}
```

**流程**：客户端收到这个 JSON → 真的去读那个文件 → 把内容返回给 LLM → LLM 基于文件内容继续推理。

**比喻**：Function Calling 就是大脑告诉手「去拿那个杯子」的方式。

> 工具层设计的核心在于容错性，不能给 Agent 无限制的高危权限（如 rm -rf /），必须在Loop 中设置人工介入（Human-in-the-loop）断点。现在比较流行的做法是对 I/O 操作进行逐行筛查，并引入黑白名单机制。

**MCP 解决什么问题？**

> 来源：Anthropic 官方博客，2024-11-25
>
> 链接：https://www.anthropic.com/news/model-context-protocol

Function Calling 的三大痛点：

1. 每个 AI 应用（Claude、Cursor、VS Code）都要**独立集成**每个工具

2. 工具调用逻辑**散落在各种 Prompt 和代码里**，难以管理

3. 没有**认证、授权、审计日志** —— 企业场景基本不可用

MCP 的设计：

1. **Server 端定义工具**，所有 Client(客户端) 自动发现

2. **协议通信**，不是 JSON 轮询 —— Server 控制工具执行边界

3. 支持**认证、授权、审计日志**

| 维度     | Function Calling                      | MCP                           |
| -------- | ------------------------------------- | ----------------------------- |
| 本质     | JSON 轮询                             | 协议通信                      |
| 工具管理 | 每个 Client 独立集成                  | Server 定义，Client 发现      |
| 安全性   | 模型输出 JSON → 客户端执行 → 注入风险 | Server 端控制边界             |
| 跨应用   | 每个应用单独集成                      | 一次 Server，所有 Client 共用 |
| 企业能力 | 无原生认证/审计                       | 内置认证、授权、审计          |

> **注意**：MCP 的本质是将 Agent 从单一的 Loop 接入到标准化的‘外部感官总线’上。（比如，让 Agent 深入企业内部系统）
>
> 比喻：
>
> Function Calling是传纸条 —— 你写'帮我查天气'，对方查完把结果递回来。
>
> MCP 是打电话——你拨通一个服务，它告诉你'我有这些能力，你可以用'。

### 总结

```Plain
1. Agent ≠ 高级 ChatGPT
   Agent = LLM 大脑 + 上下文记忆 + 工具调用 + 自主循环

2. Agent 的底层机制：ReAct 循环
   感知（看）→ 思考（想）→ 行动（做）→ 观察/反馈（验）→ 循环

3. 所有 Agent 名词都能放进三域地图
   上下文域（知道什么）、工具域（能做什么）、协议域（怎么交互）

4. 你已经看懂了一段 ReAct Agent 的核心代码（下一步自己跑起来吧）
```
